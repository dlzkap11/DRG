## 작성 내용과 판단
- **QA 폴더의 역할**: 확인 방법과 결과만 기록하고 규칙은 정하지 않는다. 규칙이 정해지지 않은 부분을 발견하면 `PROGRESS.md`에 설계 질문으로 올린다.
- **M3 체크리스트**: DEC-008과 `BotAI.cs`에서 화면으로 관찰할 수 있는 규칙을 골랐다. 특히 "HP 2~3이면 절대 방어하지 않음", "Ki 0이면 항상 Gather"처럼 한 번만 어겨도 확실한 실패인 항목을 넣었다. 비율(50%, 40%)은 몇 판으로 판단할 수 없어서 메모만 하도록 했다.
- **§26 추적표**: 테스트 이름만 보지 않고 본문의 준비 상태와 Assert를 읽고 판정했다. 명세서의 `[ ]`는 규칙 문서라 고치지 않았고, 상태는 추적표에서 관리한다.
- **UI 케이스**: 실제 UXML 요소 이름과 `BattleView.cs`의 화면 문구를 그대로 썼다. 자동 테스트와 겹치면 테스트 이름을 적었다. 겹치는 테스트가 없는 케이스(Ki 3의 Gather 비활성, 패배·무승부 문구, 연타, 키보드, 창 크기 등)가 수동 확인의 핵심이다.

## 검증 방법과 결과
- 문서 작업이라 코드 변경이 없다. 컴파일과 EditMode 테스트는 **실행하지 않았다**.
- QA 문서에 적은 테스트 이름 68개가 모두 `Assets/_Project/Tests/EditMode`에 실제 메서드로 있는지 grep으로 확인했다. 없는 이름은 0개였다.
- 체크리스트와 UI 케이스는 아직 실제 빌드로 실행하지 않았다. 빈 양식이다.

## 추적표에서 발견한 것
- §26의 17개 항목 중 16개는 자동 테스트로 충분히 확인된다. 1개(#2 모든 행동 상호작용)는 일부만 확인된다.
- 빈 곳:
  - G1: Gather+Teleport, Teleport+Teleport 조합 테스트 없음 (공격이 없어 위험 낮음)
  - G2: 상쇄 쌍이 한 턴에 둘 이상인 경우 (A↔B, C↔D) 테스트 없음 → M4 전에 검토
  - G3: 8인전 특정 상황을 직접 확인하는 테스트 없음 (무작위 시뮬레이션만) → M4
  - G4: UI의 Ki 3 Gather 비활성, 패배·무승부 종료 문구 자동 테스트 없음 → UI-03, UI-15, UI-16으로 수동 확인
  - G5: 빌드에서 seed를 알 수 없어 버그를 같은 seed로 재현할 수 없음 → 설계 질문으로 `PROGRESS.md`에 기록
